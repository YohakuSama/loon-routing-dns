> **第三方 Loon 配置分享，非 Loon 官方项目。** 面向中国大陆网络环境下的日常使用，整理分流、DNS、广告过滤和策略组。**目前仅在 Loon iOS 环境进行过测试，macOS 尚未测试。**

## 这个项目适合谁？

不少 Loon 新用户一直使用默认配置，能连接节点，却不清楚 DNS、国内外分流和远程规则该如何搭配。本项目提供一份可直接导入、也方便自行修改的完整配置，减少从零整理的工作。

它主要帮助你：

- **管理国内外流量**：常用国内服务优先直连，国外服务按策略选择节点。
- **改善部分 DNS 解析异常**：为普通 DNS、加密 DNS 与代理分流提供一套经过 iOS 实际使用测试的默认组合。
- **减少不必要的配置工作**：集成常见平台策略组、自动测速、故障转移、广告过滤和图标美化。
- **更方便地排查问题**：DNS、代理、广告过滤均可根据个人网络环境调整。

一些额外的“防 DNS 泄漏”插件未必适合每个人，也可能与已有配置冲突。本项目不依赖额外的同类插件来完成基础 DNS 与分流设置；**但不承诺绝对零 DNS 泄漏，也不保证优于所有其他方案。**

## 内置功能

- 国内常用网站直连规则及国外平台分流规则。
- AI、Google、Apple、Microsoft、YouTube、Netflix、Disney+、Spotify、TikTok、Telegram 等独立策略组。
- `Proxy` 手动选择、`Auto` 自动测速、`Fallback` 故障转移和 `Final` 最终策略。
- 第三方广告过滤规则，可通过 `AdBlock` 策略组调整。
- 默认 AdGuard 普通 DNS 与 DoH，支持自行更换。
- Qure Color 与 social-icons 彩色图标。
- IPv4 优先及 IPv6 相关配置。
- **WebRTC / STUN 泄漏风险缓解**：内置 STUN UDP 限制与 UDP 回退保护，降低部分浏览器暴露真实公网 IP 的风险。

**本项目不提供机场、代理节点或订阅链接。**

2. 打开 Loon 主界面 →「配置文件」→ 右上角「＋」→「从链接导入」，粘贴上方配置直链（推荐关闭「全覆盖更新」）。

## DNS 使用说明

本项目默认配置：

```ini
dns-server = 94.140.14.14,94.140.15.15
doh-server = https://dns.adguard-dns.com/dns-query
```

### 如何更换普通 DNS 和 DoH？

打开当前配置文件，找到 `[General]` 部分：

- **普通 DNS**：修改 `dns-server =` 后面的 IP；多个 IP 用英文逗号分隔。
- **DoH**：修改 `doh-server =` 后面的完整 HTTPS 地址。

保存并重新加载配置，然后检查解析结果。**不要只修改 DNS 地址，却忘记检查应用内的 DoH 流量模式。**

### 普通 DNS 和 DoH 有什么关系？

普通 DNS 通常使用未加密查询；DoH 通过 HTTPS 加密 DNS 请求。Loon 同时配置两者时，可优先使用加密 DNS；在允许回退的情况下，加密 DNS 失败后可能使用普通 DNS。

因此，**保留普通 DNS 不代表每次都使用明文 DNS；配置 DoH 也不代表绝对不会出现普通 DNS 查询。** 代理节点的地址解析、系统流量和其他应用的独立 DNS 行为也可能影响测试结果。

Loon 除 DoH 外，还支持普通 DNS、**DoQ** 和 **DoH3** 等方式。不同协议没有绝对的速度排名，选稳定可用的即可。

### DNS 中的 SYSTEM 是什么？建议开启吗？

这里的 **`SYSTEM` 专指 Loon 普通 DNS 配置中的 `system`**，例如 `dns-server = system,223.5.5.5`。它表示使用设备当前网络环境的系统 DNS 解析器，可能来自 Wi-Fi 路由器、运营商或设备的网络设置，**不是** `Final` 策略组、系统代理开关，也不是名为 SYSTEM 的机场节点。

**本项目默认不添加 `system`**，主要为了让 DNS 上游更明确，便于测试和排查。它不意味着系统 DNS 一定不安全，也不代表加入 `system` 就必然泄漏。

如果需要解析企业内网、校园网或局域网专用域名，可以根据需要启用。**不使用 SYSTEM 也不等于完全禁止系统层面的 DNS 流量。**

### 建议关闭「查询回落」吗？怎么关？

如果你重视 DNS 隐私，**建议先确认加密 DNS 稳定可用，再关闭加密 DNS 失败后回退普通 DNS 的选项**。

在 **Loon → 当前配置相关的「DNS 服务器」设置页面**，找到加密 DNS 的**「查询回落」/「查詢回落」**（不同语言或版本可能显示为「查询回退」或类似名称），将其关闭。具体入口名称以你的 Loon 版本为准。

**关闭后的代价**：加密 DNS 一旦不可用，部分网站可能无法解析。不要把这一设置理解成绝对的防泄漏开关。

### DoH 的 DIRECT 和 RULE 怎么选？

- **DIRECT（直连）**：该 DoH 在中国大陆可以稳定裸连时优先尝试。
- **RULE（规则）**：该 DoH 无法稳定直连时可尝试，**但要确认分流结果确实经过可用代理**。RULE 不等于强制代理。

本项目默认 AdGuard DoH 在作者的大陆网络环境中使用 `RULE` 测试正常；其他用户可以根据自身网络调整。

**延迟方面**：经代理访问 DoH 可能增加首次 DNS 查询耗时，但 DNS 缓存与连接复用会降低影响；DNS 延迟也不等于网页整体延迟或游戏实时延迟。

## 广告过滤：AdBlock 应该选 REJECT 还是 Proxy？

本项目的 `AdBlock` 是一个**广告规则策略组**，并不是代理节点。广告过滤远程规则匹配到的请求，会交给这个策略组决定如何处理。

| AdBlock 选项 | 作用 | 适合谁 |
|---|---|---|
| **REJECT** | 直接拒绝命中广告规则的连接，实现规则层面的广告或跟踪请求拦截 | **推荐默认选择** |
| **Proxy** | 将命中的请求交给 `Proxy` 策略组，通过所选代理继续访问 | 广告规则误拦截网站时，用于临时排查 |

**建议：日常选择 `REJECT`。** 如果出现登录、支付、图片或网页组件异常，可临时改为 `Proxy` 测试是否为广告规则误拦截。改成 `Proxy` 后，命中的请求通常不会再被这组广告规则拒绝，**不是“代理过滤广告”**。问题确认后，可针对误拦截域名调整规则，而不是长期关闭全部拦截。

广告过滤效果取决于规则覆盖范围，不保证去除所有应用内广告；部分规则也可能误拦截正常服务。

## 为什么选这些远程规则？

这份配置不是简单把网上能找到的规则全部装进去，而是按日常需求做分工，避免新手自己组合大量来源、难以维护。

- **anti-AD：负责广告过滤。** 使用专门的广告域名规则，统一交给 `AdBlock` 策略组控制。选择它是为了让广告拦截可以独立开关和排查，而不与普通代理策略混在一起。
- **Loyalsoldier：补充国内直连。** 对国内常用域名提供直接连接的规则参考，减少本来可以直连的国内服务误走代理。它与按 IP 地理位置判断的规则形成互补。
- **blackmatrix7：负责国外平台和服务分类。** 覆盖 AI、搜索、流媒体、社交、苹果服务、游戏和支付等常见场景，便于给不同平台选择不同节点，也减少手动维护大量域名的工作。
- **Qure Color 与 social-icons：负责界面美化。** 统一策略组图标风格，让新用户更容易识别不同服务；这些图标不参与 DNS 解析或流量分流。

**为什么不把所有规则都交给一个来源？** 广告拦截、国内直连和平台分流的目标不同，分开维护更容易理解、调整和排查。远程规则之间仍可能有交叉，实际命中以 Loon 的规则处理结果为准，并非规则越多越快、越安全。

**更新提示：** 远程规则由第三方维护，建议保持正常更新；它们与主配置文件的「托管 / 全覆盖更新」不是同一件事。远程规则下载失败时，应检查网络、规则链接及对应策略组是否有效。

## UDP 处理说明

本配置默认限制 STUN 探测，并在代理节点无法处理 UDP 时选择拒绝回退，目的是降低部分 WebRTC 真实 IP 暴露及 UDP 意外直连的风险。**这不代表全面禁用 UDP，也不能保证完全防止泄漏。** 部分游戏、语音视频或 P2P 功能可能受影响，建议按实际使用情况测试。

## DNS 泄漏与 WebRTC 泄漏：有什么区别？

两者都与隐私有关，但**不是同一回事**，也不能只通过一个网站的检测结果就断定完全安全。

| 类型 | 可能暴露什么 | 可能造成的影响 | 本项目的处理方向 |
|---|---|---|---|
| **DNS 泄漏** | 域名查询及使用的 DNS 解析路径 | 本地网络、运营商或第三方 DNS 可能获知访问过哪些域名；也可能遇到解析干扰 | 提供加密 DNS、DNS 分流及可自行调整的回退设置 |
| **WebRTC 泄漏** | 浏览器通过实时通信机制获取的网络地址，某些情况下包括真实公网 IP | 网站可能发现与代理出口不同的真实网络地址，从而削弱代理隐藏 IP 的效果 | 限制 STUN UDP，并避免不支持代理 UDP 时直接回退 |

### WebRTC 处理前后有什么区别？

WebRTC 是浏览器语音、视频和点对点通信使用的技术。它本身不是恶意功能，但某些浏览器可能借助 STUN 发现设备对外可见的 IP。**即使普通网页显示的是代理节点 IP，WebRTC 也可能暴露另一条网络路径上的真实公网 IP。**

本项目已经内置针对这类风险的保护设置，主要作用是**减少 STUN UDP 引发的 WebRTC IP 暴露风险**，并降低 UDP 在代理不可用时意外直连的可能性。

- **没有相关保护时**：在特定浏览器、网络和代理组合下，WebRTC 可能发现真实公网 IP。
- **启用本项目保护后**：部分 STUN 探测会受到限制，能够降低这一类暴露风险。
- **可能的代价**：部分网页语音、视频会议、P2P 通信、游戏语音或需要 UDP 的功能可能受到影响。

**重要：这不是“完全关闭 WebRTC”，也不等于 100% 防止所有 WebRTC 泄漏。** 浏览器自身的 WebRTC 实现、其他发现地址的方式以及未经过 Loon 的流量，仍需单独检查。若你非常依赖实时音视频，请先测试兼容性。

### WebRTC 泄漏检测与影响因素

推荐使用以下网站交叉测试（测试前先开启 Loon，并确认普通网页显示的是预期代理出口 IP）：

| 网站 | 地址 | 主要用途 |
|---|---|---|
| BrowserLeaks WebRTC | https://browserleaks.com/webrtc | 查看 WebRTC 检测到的公网、局域网地址及浏览器支持情况 |
| IPLeak | https://ipleak.net/ | 对比普通网页出口 IP 与 WebRTC 检测结果 |
| BrowserLeaks.io WebRTC | https://browserleaks.io/tests/webrtc-leak | 补充检查 WebRTC 地址暴露情况 |

**如何判断？** 如果 WebRTC 检测显示了与代理出口不同、且确认属于自己实际网络的**真实公网 IPv4 / IPv6**，就需要怀疑存在 WebRTC IP 泄漏。只显示代理节点公网 IP、局域网私有地址或浏览器用于隐藏局域网地址的随机 `.local` / mDNS 名称，**不能直接认定真实公网 IP 泄漏**。测试为空也不等于绝对安全，可能是浏览器限制、检测不支持或网络请求失败。

**WebRTC 结果受到多种因素共同影响**，包括浏览器及其版本、WebRTC 隐私设置、iOS / macOS 系统网络行为、Wi-Fi 与蜂窝网络、IPv4 / IPv6、STUN / TURN、Loon 的流量接管与分流方式、节点的 UDP 支持情况，以及其他 VPN、代理、浏览器扩展和应用自身设置。不同浏览器或不同网络下的结果可能不同。

**如果检测到疑似泄漏，不代表一定是机场节点或本配置造成的。** 建议先对比真实公网 IP 与代理出口 IP，再换浏览器、切换 Wi-Fi / 蜂窝网络复测，并检查浏览器设置、系统网络与 Loon 连接日志。项目已包含降低部分 STUN / UDP 泄漏风险的设置，但无法替代浏览器与系统层面的隐私保护，也不保证所有 WebRTC 场景完全无泄漏。

### DNS 泄漏检测网站

建议至少使用两个网站交叉检查，**测试前先确认 Loon 已开启，并选择了预期的代理节点**：

| 网站 | 地址 | 用途 |
|---|---|---|
| DNSLeakTest | https://www.dnsleaktest.com/ | 提供 Standard 和 Extended 两种 DNS 检测，建议选择 Extended |
| BrowserLeaks DNS | https://browserleaks.com/dns | 查看 DNS 解析器及其 IP、运营组织等信息 |
| IPLeak | https://ipleak.net/ | 同时检查公网出口 IP、DNS 和 WebRTC |
| BrowserLeaks WebRTC | https://browserleaks.com/webrtc | 专门查看 WebRTC 可能暴露的网络地址 |

### 如何判断 DNS 是否泄漏？

**首先确定你希望 DNS 走哪条路径。** 本项目允许国内网站直连，也允许用户自行选择 DoH 的 `DIRECT` 或 `RULE`。因此，不能简单地认为“DNS 检测结果必须全部来自日本”，也不能把所有中国大陆 DNS 都直接判为泄漏。

| 检测结果 | 判断 | 原因 |
|---|---|---|
| 预期通过代理解析，但检测出现了本地运营商或路由器提供的 DNS | **高度怀疑 DNS 泄漏** | DNS 可能绕过预期代理路径；需结合 Loon 日志确认 |
| 预期仅使用指定加密 DNS，却检测到不认识的解析服务商 | **需要排查** | 可能是回落、其他 DNS、浏览器独立解析或上游转发，不能只凭名称下结论 |
| 使用 AdGuard DoH，却出现 DataCamp、其他云服务商的 IP | **不一定是泄漏** | DNS 服务商可能使用其他公司的服务器或出口 IP；需要核对 IP 归属与实际解析路径 |
| 出现 Cloudflare、Google 的多个 IPv4 / IPv6 DNS 地址 | **不一定是泄漏** | 公共 DNS 可能有多个递归解析出口；IPv6 DNS 地址不等于设备的真实 IPv6 地址 |
| DNS 所在国家与代理节点国家不同 | **不一定是泄漏** | DNS 解析器与网页代理出口可以位于不同地区 |
| 只出现预期的解析服务商，且未观察到本地 DNS 绕行 | **暂未发现明显异常** | 这是积极信号，但单次网页检测不能证明绝对没有泄漏 |
| 检测显示 0 个 DNS 服务器或测试报错 | **不能据此认定安全** | 可能是测试被阻断、脚本未运行或解析失败 |

**判断核心不是“IP 数量多不多”或“是不是外国 IP”，而是 DNS 查询有没有违背你设定的路径，意外经过本地运营商或其他未授权解析渠道。** 检测网站通常看到的是递归 DNS 访问权威服务器时的出口地址，**不一定是你在 Loon 中填写的 DoH 服务器 IP**。

### 推荐测试步骤

1. **确认出口**：先打开 https://ipleak.net/ ，核对网页显示的公网 IP 是否为预期的代理节点。不要把这里的网页出口 IP 与下方 DNS IP 混为一谈。
2. **测试 DNS**：打开 https://www.dnsleaktest.com/ ，选择 **Extended test**；再用 https://browserleaks.com/dns 交叉检查。
3. **核对解析器**：查看出现的 DNS 运营商和 IP 是否符合自己配置的 DNS 服务及路由预期。不要仅凭国家、IP 数量或 IPv4/IPv6 判断。
4. **检查 WebRTC**：访问 https://browserleaks.com/webrtc 和 https://ipleak.net/ ，对比普通网页出口与 WebRTC 公网 IP。出现其他地址时先核实归属，不能仅凭 IP 不同就认定是本配置造成。
5. **复测**：在 Wi-Fi 与蜂窝网络下分别测试，必要时切换节点并查看 Loon 连接日志；若发现异常，重点检查 DNS 模式、查询回落、浏览器独立 DNS 和分流规则。

### 发现疑似泄漏后怎么办？

先确认 DoH 服务器是否可用，以及 `DIRECT` / `RULE` 是否符合当前网络环境；再检查是否开启了「查询回落」、是否配置了 `system` 或其他 DNS、浏览器是否自行启用了独立 DoH。**不要为了让测试结果只显示某一个国家，就盲目关闭国内直连或 IPv6。**

DNS 泄漏检测和 WebRTC 检测只能辅助判断；要确定某一次查询是否绕过 Loon，仍需结合实际网络流量与连接日志。本项目不能保证在所有设备和网络上实现绝对零泄漏。

## 测试范围与隐私说明

本项目的 DNS 调整与验证目前基于**中国大陆网络环境下的 Loon iOS**。在所测试的网络和代理节点组合中，DNS 测试表现有所改善，未观察到此前担心的明显异常，但**这不构成所有网络、所有应用“绝对无 DNS 泄漏”的保证**。

**WebRTC 专项测试尚未完成。** 配置包含 STUN/UDP 保护，但不能据此宣称所有浏览器都不存在 WebRTC 泄漏。

**macOS 版本未测试。** 即使配置可以导入 macOS，系统网络行为、DNS 路径和实际效果也可能不同，请自行验证。

DNS 检测页面出现 Cloudflare、Google 等解析器 IP，不一定代表真实公网 IP 泄漏；需要结合代理出口 IP、DNS 检测和连接日志判断。
