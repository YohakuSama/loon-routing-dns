# 2026-10-18 自维护规则库专项审计（候选版本）

## 审计范围和结果

本次针对用户报告的“BrowserLeaks 页面显示真实公网 IP”进行**实际发布文件与生成逻辑**检查，而非只看仓库配置语法。检查了 `ChinaDirect.list`、`AdBlock.list`、`AI.list`、`Google.list` 的实际规则，以及 `rules/generated/audit.json`、规则来源及生成器。

| 指标 | 审计发现 |
| --- | --- |
| 候选规则源 | 87 个 |
| 候选分组 | 33 个 |
| ChinaDirect 原始生成规则 | 123,011 条 |
| ChinaDirect 修复后规则 | **123,010 条** |
| AdBlock 规则 | 77,213 条 |
| 原审计跨策略精确冲突 | 159 条 |
| 原审计不同策略父子域名覆盖 | 7,421 条 |
| 确认的高风险误分类 | **`DOMAIN-SUFFIX,browserleaks.com` 被归到 `ChinaDirect → DIRECT`** |

### 已确认的来源

- 上游输入：`bm-chinamaxnomedia-domain`，对应 blackmatrix7 的 `ChinaMaxNoMedia_Domain.list`，包含 `.browserleaks.com`。
- 生成器将其标准化为 `DOMAIN-SUFFIX,browserleaks.com`，并写入本项目 `rules/generated/ChinaDirect.list`。
- 这会使使用该生成规则库的客户端把诊断网页错误地直连，从而看到本机公网 IP；**网页出口误分类与 DNS 是否明文泄漏不是同一问题**。
- 当前正式 `LoonKit.lcf` 另有本地 `browserleaks.com → Proxy` 覆盖规则，但它只解决当前客户端，不会清理自有规则库本身。故必须同时修复生成器和发布文件。

### 已完成的修复

1. 自有库原始发布列表删除 `DOMAIN-SUFFIX,browserleaks.com`。
2. 新建 `rules/routing_guardrails.json`，显式列出关键 DNS / IP 检测站点，禁止任何候选 `DIRECT` 分组用精确域名、域名后缀或关键词规则覆盖它们。
3. 生成器 `scripts/build_composite_rules.py` 在入口过滤、记录来源和行号；发布前再次断言，不允许命中受保护域名的 `DIRECT` 规则存活。
4. 新增回归测试，检查过滤行为、候选 **实际 `ChinaDirect.list` 文件**、审计状态、移除记录及规则数，防止下一次上游刷新复发。
5. `audit.json` 修正为 `STAGED_CANDIDATE`，避免把未启用的候选库标成已投入正式配置。

### 暂不视为已解决的问题

- `audit.json` 中 159 个跨策略精确冲突和 7,421 个父子规则覆盖冲突为**候选原始规则的审计指标**，不等于分别有 159/7,421 个实际错误。尤其 `ChinaDirect` 的广泛 `.cn` 规则会产生大量覆盖警告。应按真实匹配优先级、业务范围和流量日志逐类审查。
- 广告/隐私名单有大量拦截项，仍需登录、支付、验证码、系统更新和共享 CDN 回归测试。
- 此次严格检查的关键直连误分类及政策门槛不构成对所有数十万条规则**逐条语义正确**的认证。
- 自有复合库仍未被正式 `LoonKit.lcf` 默认加载：要重启默认使用，除了生成文件通过 CI，还需要在真实 iPhone 上验证国内外分流、DNS 解析、网页出口、IPv6、广告误杀、流媒体与资源下载，然后单独批准启用 PR。

## 正确的维护流程

**上游采集 → 规范化 → 自有规则过滤和冲突分析 → 生成物安全校验 → CI → 真机灰度 → 正式配置引用**。

来自上游的不准确条目应在自有生成层修正，而不依赖外部上游先改，更不能只把例外塞进 `LoonKit.lcf` 就视为维护完成。

本报告及测试不承诺“所有站点无 DNS 泄漏”。具体网络出站还需结合 Loon 请求/DNS 日志确认。
